# Risks and Operations

## 1. Low-latency, надёжность и деградация

### Edge-first hot path

Критический путь выполняется на edge-узле проходной: detection → quality → liveness → embedding → ANN search → access policy → decision. Это уменьшает сетевую зависимость и позволяет ориентироваться на p95 менее 1 секунды.

Центральные сервисы не должны находиться в синхронном hot path для каждого прохода. Они используются для обновления моделей, biometric templates, access policy, централизованного аудита и мониторинга.

### Локальный кеш

На edge хранится зашифрованный локальный кеш:
- biometric embeddings;
- ANN index;
- минимальная информация об employee_id;
- актуальные access policies;
- версия и timestamp последнего обновления.

Обновления доставляются инкрементально. Критические revoke-события, например увольнение сотрудника или блокировка доступа, имеют повышенный приоритет.

### Потеря сети

При потере связи edge продолжает выполнять CV inference локально.

Если кеш достаточно свежий и все проверки уверенно пройдены, допускается работа согласно offline policy.

Если возраст кеша превышает установленный safety TTL, система не должна автоматически открывать турникет. Решение переводится в `manual_review`, а карта-пропуск используется как fallback.

Это особенно важно для сценария, когда доступ сотрудника уже отозван в центральной системе, но изменение ещё не дошло до edge.

### Недоступность модели или базы

Если face detector, liveness, embedding model или ANN index недоступны/повреждены, система переходит в fail-safe режим:

- автоматический `allow` отключается;
- сотрудник использует карту;
- при необходимости подключается охрана;
- ошибка фиксируется в monitoring и audit log.

Отказ AI-компонента не должен блокировать физический доступ всем сотрудникам, пока существует безопасный резервный механизм.

## 2. Идемпотентность и турникет

Каждое событие имеет уникальный `event_id`, а принятое решение — `decision_id`.

Повторная обработка одного `event_id` должна возвращать существующее решение, а не создавать новое.

Команда открытия содержит `decision_id`. Turnstile gateway должен отклонять повтор команды с уже обработанным идентификатором.

Таким образом retry после сетевого timeout не приводит к двойному открытию турникета.

## 3. Offline audit

Во время отсутствия сети audit events записываются в локальную durable queue.

После восстановления связи события асинхронно отправляются в центральный Audit Service.

Каждая запись содержит:
- event_id;
- timestamp;
- decision;
- reasons;
- model/index/policy version;
- degraded mode;
- latency.

Доставка должна быть идемпотентной, чтобы повторная синхронизация не создавала дубликаты.

# Privacy, Safety and Governance

## 4. Биометрические данные

Face embeddings являются биометрическими и чувствительными данными даже без хранения исходной фотографии.

Основной принцип — data minimization.

В целевой системе постоянно хранятся biometric templates/embeddings, необходимые для распознавания, но не постоянный архив кадров со всех проходов.

Исходные изображения по умолчанию удаляются после обработки. Если для расследования инцидентов требуется кратковременное хранение, используется отдельный encrypted storage с ограниченным TTL, строгими правами доступа и юридически согласованной политикой.

## 5. Защита данных

Biometric templates должны:

- шифроваться при хранении;
- передаваться только по защищённому каналу;
- иметь строгий RBAC;
- быть недоступны обычным пользователям и операторам;
- иметь audit trail операций чтения/изменения;
- храниться отдельно от избыточных персональных данных.

Ключи шифрования не должны храниться вместе с самой базой embeddings.

Edge-узлы рассматриваются как потенциально физически доступные злоумышленнику, поэтому локальный biometric cache также должен быть зашифрован.

Это снижает последствия кражи edge-устройства.

## 6. Model inversion и утечка templates

Embedding нельзя считать анонимными данными.

Для снижения риска:

- минимизируется число копий templates;
- запрещается выгрузка embeddings через пользовательские API;
- используется строгая service-to-service authentication;
- edge получает только необходимую часть данных;
- доступ и массовые чтения логируются;
- используются rate limits;
- секреты и ключи хранятся отдельно;
- проводится security review выбранной face-recognition модели и template storage.

Компрометация biometric template опаснее утечки пароля: лицо нельзя просто «сменить», поэтому требования к защите повышенные.

## 7. Удаление сотрудника и отзыв доступа

Центральная Identity System является source of truth.

При увольнении, отзыве доступа или согласия:

1. центральный доступ блокируется;
2. создаётся high-priority revoke event;
3. biometric template удаляется/деактивируется централизованно;
4. изменение распространяется на все edge-узлы;
5. edge подтверждает применение новой версии;
6. операция фиксируется в audit log.

Если edge слишком долго не получает обновления, он переходит в degraded mode и перестаёт автоматически разрешать проход по потенциально устаревшей базе.

## 8. Human-in-the-loop

Система не должна полностью автоматически разрешать физический доступ при неопределённости.

Обязательный `manual_review` используется при:

- пограничном match score;
- малом margin между кандидатами;
- сомнительном liveness;
- недостаточном качестве;
- устаревшем кеше;
- неизвестном состоянии access policy.

При manual review турникет остаётся закрытым.

Охрана использует альтернативный способ подтверждения личности — например, существующую карту или корпоративное удостоверение.

## 9. Объяснение решения сотруднику

Сотруднику не следует раскрывать внутренние thresholds, embeddings или детали anti-spoofing, которые могут облегчить обход системы.

Допустимы безопасные причины:

- «Не удалось уверенно распознать лицо»;
- «Недостаточное качество изображения»;
- «Требуется дополнительная проверка»;
- «Сервис временно работает в резервном режиме»;
- «Нет действующего разрешения на проход».

Подробные технические причины сохраняются только в защищённом audit trail.

## 10. Ключевые риски

### Security

Главный риск — false accept и spoofing.

Меры:
- высокий threshold автоматического allow;
- liveness;
- margin check;
- manual-review zone;
- shadow mode и staged rollout.

### Availability

Главный риск — отказ edge/сети/модели в пиковое время.

Меры:
- локальный inference;
- fallback на карту;
- health checks;
- мониторинг;
- fail-safe degradation.

### Privacy

Главный риск — компрометация biometric templates.

Меры:
- data minimization;
- encryption;
- RBAC;
- audit;
- ограниченное хранение;
- централизованный lifecycle templates.

### ML quality

Главный риск — ухудшение качества при изменении освещения, камер и условий съёмки.

Меры:
- validation на реальных условиях;
- мониторинг по камерам;
- drift detection;
- delayed labels;
- возможность rollback модели.

## 11. Принцип безопасного отказа

Для физического контроля доступа используется правило:

**неопределённость не является разрешением.**

Если система не может доказать с достаточной уверенностью, что одновременно выполнены условия identity, liveness и access policy, она не отправляет команду `open`.

При этом для легитимного сотрудника сохраняется безопасный fallback через карту и/или охрану.
