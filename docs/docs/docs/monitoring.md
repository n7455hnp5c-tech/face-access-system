# Monitoring

## 1. Цель мониторинга

Мониторинг должен отвечать на три вопроса:

1. Работает ли инфраструктура стабильно и укладывается ли система в SLA?
2. Не деградировало ли качество CV/ML-компонентов?
3. Решает ли система исходную бизнес-задачу: ускоряет проход без недопустимого роста рисков безопасности?

Метрики анализируются не только глобально, но и отдельно по `gate_id`, `camera_id`, версии модели и режиму online/offline.

## 2. Технические метрики

Отслеживаются:

- end-to-end latency p50/p95/p99;
- latency face detection;
- latency liveness;
- latency embedding extraction;
- latency ANN search;
- доступность камер;
- доступность edge-узлов;
- доля потерянных/повреждённых кадров;
- ошибки интеграции с турникетом;
- ошибки синхронизации с центральным сервисом;
- возраст локального employee/access cache;
- размер очереди несинхронизированных audit events;
- CPU/GPU/RAM edge-узлов.

Основной SLA:

`end-to-end latency p95 < 1 second`.

### Стартовые алерты

- p95 latency > 1 s в течение 5 минут;
- камера недоступна > 30 секунд;
- edge node недоступен;
- ANN search latency > 100 ms;
- ошибки команды турникету > 1%;
- возраст access cache превышает safety TTL;
- накопление offline audit queue выше допустимого лимита.

Конкретные значения уточняются после пилота.

## 3. ML-метрики

Основные ML-метрики:

- False Accept Rate (FAR);
- False Reject Rate (FRR);
- доля `manual_review`;
- доля отказов из-за низкого качества;
- liveness failure rate;
- подтверждённые spoofing attempts;
- распределение top-1 similarity;
- распределение margin до второго кандидата;
- доля событий без найденного лица;
- Recall@1 для identification на размеченных событиях.

Особое внимание уделяется FAR, поскольку false accept является security incident и имеет существенно более высокую стоимость, чем false reject.

## 4. Delayed labels

FAR и FRR невозможно полностью оценивать непосредственно в момент inference, поэтому используются delayed labels:

- решения охраны после manual review;
- проход по карте после face reject;
- жалобы сотрудников;
- результаты расследования security incidents;
- подтверждённые spoofing cases.

Delayed label связывается с исходным событием через `event_id`.

Метрики пересчитываются после появления новых подтверждённых labels.

## 5. Drift

Контролируется drift входных данных:

- brightness / illumination;
- blur;
- размер лица;
- head pose;
- occlusion;
- quality score;
- распределение embedding similarity;
- liveness scores.

Текущие распределения сравниваются с baseline периода пилота.

Резкое изменение не означает автоматически деградацию ML-модели: сначала необходимо определить источник изменения.

## 6. Как отличить проблему камеры от деградации модели

Метрики агрегируются отдельно по каждой камере и проходной.

Пример:

если одновременно:
- на `cam-1a` резко вырос low-quality rate;
- снизилась brightness;
- вырос blur;
- другие камеры работают нормально,

то вероятнее проблема связана с камерой, загрязнением объектива или изменением освещения, а не с глобальной деградацией recognition model.

Если ухудшение FAR/FRR наблюдается одновременно на разных исправных камерах после обновления модели, более вероятна ML-регрессия.

Поэтому dashboard должен позволять сравнивать:

`model_version × gate_id × camera_id × conditions`.

## 7. Мониторинг по условиям

FRR, manual-review rate и quality rejection анализируются отдельно для:

- normal / dim / backlight;
- разных head pose;
- масок;
- очков;
- различных камер;
- времени суток.

Это позволяет обнаружить ситуацию, когда общая метрика остаётся приемлемой, но система плохо работает в конкретном эксплуатационном сценарии.

## 8. Бизнес-метрики

Контролируются:

- среднее и p95 время прохода;
- среднее время ожидания в очереди;
- доля автоматических проходов;
- доля ручных проверок;
- количество обращений к охране;
- количество fallback-проходов по карте;
- число подтверждённых security incidents.

Ключевая цель — уменьшить время безопасного прохода и нагрузку на охрану, не увеличивая неприемлемо риск false accept.

## 9. Audit trail

Каждый access event должен быть воспроизводим для расследования.

По `event_id` должны быть доступны:

- timestamp;
- gate_id;
- camera_id;
- employee candidate;
- quality score;
- liveness score;
- match score;
- second-best margin;
- версия модели;
- версия ANN index/access policy;
- online/offline status;
- итоговое решение;
- reasons;
- latency;
- turnstile command;
- результат manual review, если был.

Это позволяет ответить не только на вопрос «что решила система», но и «почему она приняла это решение».

## 10. Реакция на алерты

### Рост latency

Проверить:
1. GPU/CPU edge;
2. latency отдельных моделей;
3. ANN index;
4. интеграцию с турникетом;
5. сетевые зависимости.

При необходимости система переводится в degraded/fallback mode.

### Рост FRR

Проверить:
1. конкретные камеры и проходные;
2. quality distribution;
3. освещение;
4. версии моделей;
5. изменения threshold.

Если причина не локализована, остановить дальнейший rollout и использовать карту как fallback.

### Рост FAR / подтверждённый false accept

Это security alert высокого приоритета.

Действия:
1. зафиксировать и расследовать audit trail;
2. временно ужесточить или отключить автоматический `allow`, если риск системный;
3. проверить модель, thresholds, liveness и access policy;
4. при необходимости откатить модель/конфигурацию.

## 11. Проверка исходной цели

Успех системы нельзя определять только ML-метриками.

На пилоте сравниваются baseline и новая система по:

- времени прохода;
- очередям в пиковые часы;
- числу ручных разборов;
- доле успешных автоматических проходов;
- FRR;
- подтверждённым false accepts;
- p95 latency.

Если система показывает высокую accuracy, но не уменьшает очередь или создаёт чрезмерное число manual reviews, исходная бизнес-задача не решена.
