# AI Usage

## Использование AI-инструментов

При выполнении задания я использовала ChatGPT как вспомогательный инструмент. AI применялся для ускорения декомпозиции задачи, обсуждения архитектурных вариантов, подготовки минимального PoC и проверки полноты документации.

При этом ключевые решения по безопасности и логике системы рассматривались отдельно: предложения AI не принимались автоматически, особенно если они могли привести к небезопасному автоматическому открытию турникета.

## 1. Понимание задачи и декомпозиция

AI помог разложить исходный кейс на несколько частей:

- системная архитектура;
- CV/ML pipeline;
- decision engine;
- offline/degraded mode;
- мониторинг;
- privacy и security;
- минимальный PoC.

После декомпозиции я выбрала edge-first архитектуру для критического пути, поскольку требование p95 < 1 секунды и возможность потери сети делают постоянную зависимость от центрального сервиса нежелательной.

## 2. Проектирование архитектуры

AI использовался для обсуждения вариантов:

- edge inference;
- central inference;
- hybrid architecture.

В итоговом варианте критический inference и принятие решения выполняются на edge, а центральная система отвечает за lifecycle сотрудников, обновление embeddings и access policy, централизованный audit и monitoring.

Основная причина выбора — снижение latency и возможность продолжать ограниченную работу при потере сети.

При этом offline-режим не должен означать безусловный доступ: при слишком старом кеше система переходит в manual review/fallback.

## 3. Выбор CV/ML-подходов

С помощью AI был сформирован baseline pipeline:

`face detection → quality assessment → alignment → liveness → embedding → ANN search → decision engine`.

Я отдельно зафиксировала разделение между ML-моделями и правилами принятия решения.

Модель предоставляет оценки качества, liveness и similarity, но непосредственно команду открытия турникета формирует Decision Engine с учётом порогов и access policy.

Для one-to-many поиска был выбран ANN-подход (например, FAISS/HNSW), поскольку полный перебор плохо масштабируется до сотен тысяч biometric templates.

## 4. Разработка PoC

AI помог подготовить минимальный Python PoC.

В PoC намеренно не используются реальные лица и биометрические данные.

Замоканы:

- face embeddings;
- quality score;
- liveness score;
- employee database.

Реализованы:

- cosine similarity;
- поиск кандидата;
- threshold-based decision engine;
- `allow / manual_review / deny`;
- turnstile command;
- audit log;
- smoke tests.

Happy path демонстрирует уверенное совпадение и `allow`.

Risky path демонстрирует offline edge с устаревшим кешем. Несмотря на хорошее совпадение лица, система не открывает турникет и возвращает `manual_review`.

Таким образом PoC проверяет прежде всего safety-критичную логику архитектуры, а не качество конкретной face-recognition модели.

## 5. Тестирование и документация

AI использовался для:

- формирования smoke tests;
- проверки наличия happy и risky paths;
- структурирования ML-документации;
- перечисления monitoring metrics;
- поиска failure modes;
- проверки требований задания по обязательным артефактам.

PoC был фактически запущен после добавления в репозиторий. Smoke tests подтвердили ожидаемое поведение обоих сценариев.

## 6. Примеры ошибок и ограничений AI

### Ошибка 1: слишком большой объём реализации

На раннем этапе AI предлагал более сложный вариант с реальными CV-библиотеками и большим количеством компонентов.

Для четырёхчасового time-box это создавало риск потратить основное время на зависимости и отладку вместо системного дизайна.

Исправление: PoC был сокращён до mock CV-компонентов и реального Decision Engine.

### Ошибка 2: техническая ошибка при создании PoC

При первоначальном добавлении `poc.py` в репозиторий файл оказался неполным: вызов `run_demo()` присутствовал, а определение функции отсутствовало.

Ошибка была обнаружена фактическим запуском PoC в Google Colab: Python вернул `NameError`.

Файл был исправлен, после чего репозиторий был обновлён через `git pull`, PoC запущен повторно и smoke tests завершились успешно.

Этот случай показал, почему AI-generated code необходимо запускать и проверять, а не считать корректным только потому, что он выглядит правдоподобно.

### Ошибка 3: опасная трактовка offline-режима

При проектировании было важно не считать наличие локального embedding достаточным основанием для прохода при любой потере сети.

Это небезопасно: например, сотрудник мог быть уволен, а revoke доступа ещё не доехать до edge.

Поэтому в итоговом дизайне введены cache freshness / safety TTL. При устаревшем кеше автоматический `allow` запрещается.

## 7. Проверка безопасности AI-предложений

При работе с рекомендациями AI я использовала принцип:

**неопределённость не является разрешением на доступ.**

Я проверяла, чтобы:

- низкий confidence не приводил к `allow`;
- сомнительный liveness не компенсировался высоким face match;
- устаревший offline cache не позволял безусловно открыть турникет;
- biometric embeddings не трактовались как анонимные данные;
- embeddings и access policy имели ограниченный доступ;
- существовал human-in-the-loop для сомнительных случаев;
- карта оставалась безопасным fallback;
- решение можно было расследовать через audit trail.

Также я сознательно не использовала LLM в контуре `allow/deny`, поскольку для физического контроля доступа необходимы специализированные CV-модели и детерминированная, аудируемая decision policy.

## 8. Решения, принятые самостоятельно

AI использовался как инструмент для генерации вариантов и ускорения оформления, но итоговый scope определялся мной.

Ключевые решения:

- сделать архитектуру edge-first;
- не ставить центральный сервис в обязательный hot path;
- использовать ANN для one-to-many identification;
- разделить ML scores и Decision Engine;
- сделать false accept более дорогой ошибкой, чем false reject;
- использовать manual review как серую зону между allow и deny;
- запретить автоматический allow при небезопасном degraded mode;
- не использовать реальные биометрические данные в PoC;
- сфокусировать PoC на decision logic вместо обучения собственной CV-модели.

Основной компромисс — глубина реальной CV-реализации была сознательно уменьшена в пользу системного дизайна, безопасности и воспроизводимого end-to-end сценария.
